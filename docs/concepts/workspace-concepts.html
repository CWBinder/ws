Workspace Concepts

How objects, classifications and relationships organise a workspace.

Start here to understand the model. For documentation and learning paths, see the documentation index. Agents start with the ws skill; exact commands come from ws help and ws describe. People, organisations and records below are fictional examples.

The model Six aspects Practical guide Projects & subprojects Relations

An object is an instantiation of a concept — of which we define a few: person, organisation, event, task, document, resource, project, literature item, profile item. Classifiers give an object its address in the folder structure, the id gives it its persistent identity, edges give it its context, and the description tells a human what it is.

Everything the workspace knows lives in ~/workspace as small, plain records — one YAML file per object, one YAML file per edge. The record is obligatory and singular: every object has exactly one record, that record is the only place its truth lives, and no record means no object. Nothing enters by accident: content joins the workspace only through a deliberate ws create or add. The machinery — contracts, templates, the CLI itself — lives separately in ~/Projects/ws.

Objects come to exist in two ways, and the table's identity column shows which is which. Most records are created and owned by ws itself — a person is its YAML file, and only ws writes it. Projects and literature items are different: their files exist anyway (project.yaml, a BibTeX entry), so the catalog reads them as objects instead of duplicating them — which is why they carry natural keys instead of ULIDs, why hand-editing project.yaml is normal while hand-editing person_….yaml is not, and why merge exists only for the owned records.

Relations are first-class records (rel_<ULID>) but not objects: they are the edges between objects and never appear in the object space themselves.

Six fields are universal — every object has them: id, kind, name, type, aliases, description (type, aliases, and description may be empty). Everything beyond the core is up to the kind. Identity is the id alone — never shared, never changed. Name and aliases are doorways the resolver walks through; renaming a person breaks no edge, because edges store ids. Kind is fixed at birth and decides which classifiers and facts apply. Classifiers place the object — type is the standard one; kinds may add more (projects and literature share fields and field-specific subfields), and status is optional everywhere: written only when set, absent means active. Facts are the kind-specific truths. The description is a sentence or two of prose: searched, read, never grouped by. Edges connect the object to everything else. The core is contractual: ~/Projects/ws/contracts/objects.md defines it, and the per-kind contracts define the rest.

Provenance sits outside the six: it describes not the object but the record-keeping — which source asserted which fields, when (--source, --observed-at). Agents may file facts as a side effect of normal work precisely because every assertion is signed and dated; staleness checks in ws check are computed from it.

Taxonomies are the allowed-value lists behind the extendable classifiers — one sparse YAML file per taxonomy-bearing domain, keyed by the classifier name itself:

# ~/workspace/projects/project-taxonomy.yaml
type: [research, paper, talk, software]
fields: [physics, mathematics, computer-science, ai, humanities]
subfields:
  physics: [quantum-information, quantum-computing, spin-qubits, shuttling,
            numerics, quantum-chemistry, experimental]
  mathematics: [tooling, numerics]

fields and subfields are shared by projects and literature. Fields are broad; the nested taxonomy records which narrower subfields belong to each field. Both may be multi-valued, but stored combinations must be compatible. Every domain answers the same calls — ws <domain> taxonomy shows the values, add-type/add-field/add-subfield extend them, and the wizards offer to extend on an unknown answer — all through one engine. A taxonomy is consulted only at the front door: it feeds the wizard's options and validates flag input, but renderings mirror whatever values records actually carry. Statuses are deliberately not taxonomies — lifecycles are fixed vocabularies in the contracts, never extendable from a prompt — and kinds without curated classifiers (person, task; organisation and event types are free strings) have no taxonomy file at all, on purpose.

Folder anatomy is the taxonomies' sibling: where taxonomies curate the allowed values, the anatomy file declares the shape of every derived by-* browse tree — one ring set per domain that nests into itself. Every facet in the set gets a by-* tree at the domain root, and each value folder holds its items flat plus a ring for every facet not yet used along the path, down to a declared depth:

# ~/workspace/folder-anatomy.yaml
documents:
  rings: [type, organisation, event, project, year > month]
  depth: 2                # by-type/receipt/by-year/2026/by-month/08-August/<file>

A facet is either a classifier of the domain's own records or a kind — folders named after related objects, resolved through the relations store; year > month marks a dependent classifier that refines its parent in place, free of the depth count. One engine (ws_lib/anatomy.py) consumes the file for all domains, validates it before wiping anything, and owns every by-* directory at a domain root, so facets removed from the file disappear on rebuild. unclassified/ exists only at the first layer; deeper rings simply omit items lacking the facet, and empty rings are never created. Domains absent from the file get built-in defaults; ws check anatomy validates the file. See contracts/folder-anatomy.md.

Practical guideThe concepts, one by one

Person person_<ULID>

An identity anchor plus contact facts — deliberately thin. Who someone is to you (employer, collaborator, met-at) lives as edges, not fields. Holds: preferred_name, emails, phones, aliases, status.

ws add person Alex Example --email alex@example.org --ensure

Bare ws add person on a terminal asks for the name, then aliases, preferred name, emails, phones, and related organisations — each answer ensured and linked affiliated-with. --ensure makes creation idempotent (match by name, alias, or email); duplicates that slip through are caught by ws check and folded with merge, whose tombstones redirect old ids forever.

Organisation org_<ULID>

Companies, colleges, societies. Holds: type (college, company, society…), website, aliases, status. Organisations are never taxonomy values or classifiers on other objects — membership is always an edge.

ws add organisation Example Institute --alias Example --type institute --website institute.example.org --ensure

Event event_<ULID>

A fixed point in time and space: start, end, timezone, location, type (fair, conference…). Events are deliberately inert — a shared anchor that attendees, documents, and organising work all point at. An event never grows folders; when organising one becomes real work, pair it with an organizatorial project (below).

ws add event Community Workshop --start 2026-10-07 --location "Community Centre" --ensure

Task task_<ULID>

Quick capture. A task is a single actionable with due and priority; it gains meaning by being related to the thing it concerns — ws show relations of project:<p> assembles a project's to-dos from its edges. Planning is a pattern, not a place: event + tasks + edges.

ws create task Book meeting room --due 2026-09-15
ws relate task:book-meeting-room to event:community-workshop as prepares

Document doc_<ULID>

A file plus its registration. Ingest moves the file into documents/files/ by default (--mode copy and --mode reference exist), and the record holds path, a classification (a type from the document taxonomy and a date), and status. Derived browse folders — by-type/, by-organisation/, by-event/, by-project/, by-year/ — are symlink renderings, rebuilt, never filed into; their shape comes from the folder anatomy file's ring set, which nests into itself beneath every value (by-type/receipt/by-year/2026/by-month/08-August/). Adding classifies; relating is its own speech act:

ws add document ~/Downloads/venue-invoice.pdf --type invoice --date 2026-07-15 --non-interactive
ws relate document:venue-invoice to organisation:example-institute as issued-by

Literature literature:<ItemKey>

An adapter over the scholarly library: each item is a folder named by its citation key (Doe2025ExampleStudy). The folder name is the identity — no ULID is minted — and the files inside split cleanly: citation.bib is the bibliographic truth, info.yaml the item's workspace-local facts (its fields and subfields classifiers, keywords, summary), plus optional PDF, TeX source, and notes. Items enter via one command that detects the identifier; the wizard then asks for fields and compatible subfields (--field/--subfield for agents), and the derived views shelve items under by-author/, by-field/<field>/by-subfield/<subfield>/, by-year/, and by-project/ at the domain root. Author and year come directly from BibTeX; fields and subfields are editable classifiers. Projects cite items through references edges, not YAML lists.

Acquisition is two steps: search-arxiv turns a title into an identifier (printing the journal DOI when arXiv knows it), and add <id> --full (shorthand for --prefer-published --pdf --source) assembles the complete item. The journal BibTeX becomes the main citation.bib — the one you cite from — while the arXiv form is always kept beside it, never lost. The e-print source is downloaded and extracted (the figures ship inside it), and the PDF is fetched journal-first with the arXiv PDF as fallback: the best available, without you deciding. Each piece is also available piecemeal later (download-pdf, download-source, enrich), so nothing forces the choice at add time.

items/<ItemKey>/
  citation.bib               journal BibTeX — the citation you cite from
  source/arxiv/citation.bib  the arXiv form, kept separately
  source/arxiv/files/        extracted TeX source; figures live here
  paper.pdf                  open-access journal PDF, else arXiv
  references.txt             cited-work identifiers, fetchable
  info.yaml                  workspace-local facts: fields, subfields, keywords, summary

Citations are the deliberate exception to edges: a paper's reference list is an extracted fact, not curated knowledge — most cited works aren't in the library, so they are stored as an identifier list on the item (references.txt, fetchable from Semantic Scholar) and the in-library overlap is computed on demand, never stored. Rare deliberate paper-to-paper assertions (supersedes, published-version-of) may still be ws relate edges.

ws literature search-arxiv numerical methods
ws add literature <ARXIV-ID> --full --field mathematics --subfield numerics
ws edit literature:<ItemKey> --add-subfield numerics
ws literature citations literature:<ItemKey> --in-library     # cited works you hold, as item keys
ws literature cited-by literature:<ItemKey>                   # library items citing this one
ws literature views rebuild

Project project:<name>

The one container: any bounded undertaking that accumulates work-product in a folder and has a lifecycle. Nothing in the definition is scientific — a conference presence is as much a project as a simulation. Projects live in the flat store projects/items/, and the folder name is the identity — physical grouping folders are retired, so reorganising never changes an identity; all ordering belongs to classifiers and edges, rendered in the by-* trees at the domain root, shaped by the folder anatomy file (research projects shelve by supporting organisation, organisational ones and talks by related event; by-organisation nests org then type).

Classifiers: type — research, paper, talk, software, teaching, organizatorial, other; broad fields and controlled subfields — from the shared workspace vocabulary (for example physics / spin-qubits or mathematics / tooling); status — idea, active, paused, complete, archived. Every project carries project.yaml, README.md, AGENTS.md, CLAUDE.md, .gitignore, its own git repository, and only sanctioned optional folders (code/ paper/ data/ docs/ refs/ notes/ out/ tmp/).

ws create project                       # wizard: name, type, then type-aware questions
ws create project community-workshop --type organizatorial --non-interactive
ws list projects --type research --status active
ws projects views rebuild

The wizard's interview lives in code, not in a data file: every question is written once, and a small routing table maps each project type to the set of questions that apply — research gets the code/venv/data battery, a talk only "has slides?", organizatorial asks which organisations it is for and which event it organises, creating those edges on the spot. The taxonomy's only role is supplying the allowed answers for three questions (Type, Fields, Subfields, with the extend-offer on unknown values); the rest draw on different sources — free text (title, description, keywords), yes/no setup flags, and references that must resolve to existing objects (dependencies, literature keys, organisations).

The closing questions record conceptual links as edges: if a mechanism executes it, it's a fact; if it merely states a connection, it's an edge. "Depends on" and "related" answers become depends-on/related relations (the old depends_on:/related: lists are read-only legacy). Cross-project code reuse is the fact side: --use-project project:example-library records a package dependency in project.yaml, ws projects install creates the venv and runs pip install -e for each recorded dependency — and recording one also creates its depends-on edge, so the connection is stated once.

Subproject

A project co-located inside another project to borrow its virtual environment — a concept whose existence is justified by coding projects. The canonical case: a simulation toolkit is the main project; the paper about it lives inside as a subproject, so its scripts and figures run in the toolkit’s .venv — but the paper’s history does not belong in the toolkit’s repository, and the paper absolutely wants a history of its own.

So the arrangement is precise. Identity: it is a project — project:<parent>/<path>, fully resolvable and relatable to documents, events, organisations like any other object. Environment: borrowed — no .venv of its own; subproject.yaml (never project.yaml) records venv: ../../.venv, and ws projects install run inside it sets up the parent’s environment. History: its own — creation runs git init in the subproject and appends its path to the parent’s .gitignore, so parent and subproject version themselves independently. Sub-ness is structure and environment-sharing, never identity; it stays out of ws list projects, and ws show project:<parent> lists it.

ws create subproject methods-paper --project project:simulation-toolkit

ContextHow concepts relate — and where that lives

Every cross-domain connection is one small YAML record in the workspace-root store ~/workspace/relations/ — one file per edge, scanned per invocation, no database:

# relations/rel_<ULID>.yaml
subject:  person_<ULID>           # resolved from person:alex-example
object:   org_<ULID>              # resolved from organisation:example-institute
relation: member-of                # free-form kebab-case — no fixed vocabulary
valid_from: ""   valid_until: ""    # optional time-bounding
source: claude-session              # provenance

The relation type is yours to invent — supported-by, phd-student-at, vice-president, references, organises. What must exist are the endpoints: find each object with ws search and use its full kind:key reference. The stored edge holds the resolved internal identities. The command reads like a sentence, with to and as as optional grammar:

ws relate person:alex-example to organisation:example-institute as member-of
ws relate project:methods-paper to literature:Doe2025ExampleStudy as references
ws unrelate person:alex-example to organisation:example-institute as member-of

Relations are stateless assertions: an edge exists or it does not. An ended relationship is still a true relation (time-bound it with valid_until); a wrong one is deleted — unrelate removes the file and prints the exact ws relate command that restores it. Merging duplicate objects re-points their edges to the canonical record automatically.

Edges are what the renderings feed on: projects/by-organisation/ and documents/by-organisation/ materialise them as folders, every wiki page carries a “Workspace relationships” section in both directions, and the search index joins them to objects. Store an edge once; see it everywhere.

Objects hold the truth, provenance signs it, renderings display it — and only the truth is ever edited.
